## Important Issues (5 found)

1. **silent-failure-hunter**: Data inconsistency in the idempotency guard is silently repaired with `log.info` — when the schema node is not `ACTIVE` despite the KB's `activeSchemaId` pointing to it, the code patches the corruption without a `WARN` or audit trail, making prior `SET` failures permanently invisible. [SchemaRegistryService.java:120-127]

2. **silent-failure-hunter**: Hard-coded string literals `'ACTIVE'`/`'INACTIVE'` in the Cypher `SET` bypass `SchemaStatus` enum serialization — a future enum rename or custom converter silently diverges from stored values, corrupting status reads with no compiler error. [SchemaRegistryService.java:140-146]

3. **silent-failure-hunter**: `@Transactional` does not provably cover the two `Neo4jClient` queries — unless the client is explicitly enrolled in the same Spring transaction manager, the repository saves and the raw Cypher writes run in separate auto-commit sessions, making the design doc's atomicity guarantee unenforceable. [SchemaRegistryService.java:108-148]

4. **security-reviewer**: No authentication or authorization guard on the activation endpoint — any unauthenticated caller can switch the active schema for any knowledge base, now with a wider blast radius (this commit adds bulk sibling deactivation). [SchemaController.java:302-315]

5. **security-reviewer**: `activateSchema` implicitly creates a `KnowledgeBaseNode` from the caller-controlled `knowledgeBaseId` path variable with no format constraint, no length limit, and no permission check — enables arbitrary node creation via the unauthenticated endpoint. [SchemaRegistryService.java:112-119]

- **silent-failure-hunter**: Add missing status assertion in `activatingSchemaDoesNotAffectOtherKnowledgeBases` — `kb1SchemaA.getStatus()` is never checked after `kb1SchemaB` is activated, so a silent `SET` failure would not be caught [SchemaRegistryIntegrationTest.java:132-149]
