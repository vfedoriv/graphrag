## Important Issues (1)

**[type-design] Remove `setVersion(Long)` setter — `DocumentUploadNode.java:53`**

Spring Data Neo4j accesses `@Version` fields via reflection; a public setter is not needed and actively harmful. Any caller that sets an arbitrary value before `save()` will either trigger a spurious `OptimisticLockingFailureException` or silently bypass the concurrency check. No production code currently calls `setVersion` on `DocumentUploadNode` (the only `setVersion` call in the codebase is in `SchemaControllerTest` on a different type), so removing it is zero-impact:

```java
// Remove this entirely:
public void setVersion(Long version) {
    this.version = version;
}
```

## Suggestions (1)

**[code-reviewer] Verify `setStatus()` return value is not silently stale — `DocumentProcessingService.java`**

With `@Version` now active, if `setStatus()` internally calls `repository.save()` and returns the version-bumped entity, any call site that discards the return value will hold an outdated version — the next `save()` on that stale reference will throw `OptimisticLockingFailureException`. Confidence is ~70% (not a confirmed bug), but it's worth running `./mvnw -Dtest=EndToEndMvpFlowIntegrationTest test` to confirm the pipeline still passes end-to-end.

## Strengths

- **`Long` (boxed) is the correct type** for `@Version` — `null` lets Spring Data distinguish a new entity from a stored one; `long` would default to `0` and confuse the insert/update detection.
- **Cypher fix is correct and complete.** All other `neo4jClient.query()` call sites in the codebase already used separate `MATCH` clauses — no additional places need patching.
- **Version does not leak into the API.** The field is absent from `toResponse()` mapping, so it stays internal.
